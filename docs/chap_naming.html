Naming Convention

The naming conventions used throughout this book — for variables, functions, files, and the domain abbreviations that appear in the code and figures.

Local conventions

  • Variables: noun_adjective, e.g., spec_complex (complex spectrogram), trace_clean. The noun comes first (spec_complex, not complex_spec) so related names group together when sorted or tab-completed.
  • Functions: verb_noun[_adverb|_adjective], e.g., smooth_spec_boxcar, estimate_bandpower_fast.
  • Booleans / flags: prefix with is_, has_, or use_, e.g., is_complex, has_nan, use_detrend.
  • Units: when a quantity’s unit is not obvious from context, carry it as a suffix — _hz, _khz, _s, _ms, _db, _rad, _deg (e.g., shaft_hz, dur_ms) — or state the unit in the docstring. This is the cheapest defense against unit-mismatch bugs.
  • Abbreviations: spell names out, except the short forms on the approved allowlist below.
  • Docstrings: always include one. Generate a first draft with an LLM (e.g., Copilot) and revise for accuracy.

Follow Google Python Style Guide (brief)

  • Use: module_name, package_name, ClassName, method_name, ExceptionName, function_name, GLOBAL_CONSTANT_NAME, global_var_name, instance_var_name, function_parameter_name, local_var_name, query_proper_noun_for_thing, send_acronym_via_https.
  • Names must be descriptive. Avoid ambiguous abbreviations and dropped-letter shortenings — except the approved abbreviations on the allowlist below.
  • Python files must end with .py; never use dashes in filenames.

Names to avoid

  • Single letters (except standard cases: i/j/k loop counters, e in except, f file handle, private type vars like _T, or symbols matching a referenced paper’s notation).
  • __double_leading_and_trailing__ (reserved).
  • Offensive terms.
  • Redundant type suffixes (e.g., id_to_name_dict → id_to_name).

Approved abbreviations (allowlist)

An allowlist (also called a whitelist) is an explicit, closed set of permitted items: only what appears on the list is allowed, and anything not on it is rejected by default. Its opposite is a denylist (blocklist), which names what is forbidden and permits everything else. The rule above bans abbreviations in general; the table below is the only exception — use these short forms freely and spell out everything else.

Abbreviation Meaning
sig signal x[n] (preferred over signal)
freq, f frequency
fs sampling frequency (preferred over f_s)
dt sampling period
omega angular frequency \omega = 2\pi f
coef complex transform coefficient(s)
mag, phase magnitude and phase of coef
spec spectrum / spectral matrix
psd, asd power / amplitude spectral density
amp amplitude
window window function w[n]
N, M, K array lengths / dimensions
wf, ma, lh, rh wave frame, moving average, left- / right-handed

N/M/K (sizes), i/j/k (loop counters), and symbols matching a cited paper are acceptable single letters; everything else should be spelled out. Avoid a bare w — it collides with both omega and weight arrays; write window or weight.

Good vs. bad:

Good Bad
spec_complex sc, complexSpectrogram
fs samplingFrequency, f_s
n_freq nf, numF
is_complex complex_flag, cplx
shaft_hz shaft (unit unclear)

Conventions & visibility

  • “Internal” = module-internal or protected/private in a class.
  • Prefer single underscore _name for protected members; avoid __dunder privacy (name-mangling hurts readability/testing).
  • Group related classes and top-level functions in the same module.
  • Class names use CapWords; module files use lower_with_under.py.
  • Unit tests: PEP 8 names, e.g., test_<method_under_test>_<state> (underscore segments allowed after test).

File naming

  • .py extension, no dashes. If you need an executable without the extension, use a symlink or tiny shell wrapper.

Quick reference (public vs. internal)

Type Public Internal
Packages/Modules lower_with_under _lower_with_under
Classes/Exceptions CapWords _CapWords
Functions/Methods lower_with_under() _lower_with_under()
Constants (global/cls) CAPS_WITH_UNDER _CAPS_WITH_UNDER
Variables lower_with_under _lower_with_under
Params/Locals lower_with_under —

Mathematical notation (when it truly helps)

  • Short symbols are fine if they match a cited paper/algorithm.
  • Document the source of the notation (link in comment/docstring).
  • For public APIs, prefer descriptive pep8_names.
  • Silence lints narrowly: # pylint: disable=invalid-name (end-line for a few vars, or at block start for many).
